# 版本、子实验与运行实例判定规则

## 1. 三种身份必须分开

| 身份 | 例子 | 何时创建 | 是否改变 `current` | 是否消耗主版本号 |
|---|---|---|---|---|
| 主线版本 | `P-v2`、`MA-v7` | 已通过候选正式替换当前真相 | 是 | 是 |
| 子实验候选 | `P-v2-a`、`P-v2-b` | 相对同一当前版本提出不同假设 | 否 | 否 |
| 运行实例 | `run-20260717T103000Z-seed-1` | 重跑、smoke、seed、参数点、机器重试 | 否 | 否 |

硬规则：

1. 主线只允许 `PREFIX-vN`。
2. 候选只允许一个字母层级 `PREFIX-vN-a`；不得产生 `v2-a-1`、`v2-a-final`、`v2-a-v3`。
3. 重跑、seed、sweep 点和 smoke 全部使用 `run_id`，不得继续追加版本符号。
4. 每个作用域独占前缀。项目级可用 `P`；工作流用业务缩写，如 `MA`；组件用稳定组件缩写。
5. 不比较不同作用域的数字大小。`P-v5` 与 `MA-v23` 没有先后关系，除非总账中另有证据化依赖。

## 2. 新候选还是新主版本

先创建候选，不直接创建下一个主版本。候选只有满足全部晋级门后才由脚本生成下一个 `vN`。

### 可晋级的实质变化

至少命中一项：

- `code_architecture`：核心代码、接口或系统架构变化。
- `data_contract`：关键输入、数据口径或数据身份合同变化。
- `workflow_contract`：阶段顺序、处理范式或安全闸门变化。
- `business_goal`：当前业务目标变化。
- `delivery_contract`：下游接入、核心输出或交付合同变化。
- `validated_default_change`：经过验证并准备成为默认行为的配置变化。

以下变化单独出现时不得晋级：

- `parameter_only`：只调参数。
- `seed_or_retry`：seed、重跑、机器失败恢复。
- `smoke_only`：只验证入口可运行。
- `evaluation_only`：只补评估或可视化。
- `result_only`：实现和合同不变，只得到一组更好结果。

“结果明显变好”可以是晋级证据，但不能代替“当前真相发生了什么实质变化”的说明。

### 晋级门

1. 候选状态为 `passed`。
2. 候选基线仍是该作用域的 current；若 current 已变化，必须新建候选重新基于当前版本评估。
3. 至少有一种可晋级变化类型。
4. 保存验证证据，且每条证据说明“该来源证明什么”。
5. 新版本摘要能独立描述新的当前真相，不写 diff 叙述。
6. 由 `promote` 原子更新版本总账、current 视图和不可变快照。

## 3. 何时继续同一候选

以下情况继续同一 `vN-a`，只增加 `run_id`：

- 同一假设的不同 seed。
- 同一配置的故障重跑。
- smoke 后转 full。
- 同一 sweep 中的参数点。
- 只补一项指标、视频或对照视图。

以下情况新建同基线的另一个候选 `vN-b`：

- 核心假设不同。
- 改动路线可独立接受或拒绝。
- 需要并行比较且可能只有一路晋级。

若一个候选内部出现多个可独立决策的假设，停止继续增加后缀，把它拆为同基线的多个候选。

## 4. 历史与血缘

1. `events.jsonl` 是追加式历史，`state.json` 是可重建的当前物化状态。
2. 主版本父子关系只由 `promote` 或带证据的旧版本登记建立。
3. 不因版本号相邻就推断承接关系。
4. 不因目录名相似就推断分支关系。
5. 证据不足时将父版本留空，并在摘要中写“关系未知”；宁可不连线。
6. 失败、放弃和未晋级候选也永久保留结论与证据。删除大产物不得删除候选事件。

## 5. 旧项目兼容

1. 先只读盘点旧 `current`、changelog、任务清单和实验记录。
2. 初始化时用当前已确认的大版本号，例如把旧 `v24` 登记为 `MA-v24`，并把 `v24` 放入 `legacy_id`。
3. 用 `record-legacy-version` 补录有证据的旧版本；缺证据版本不猜。
4. 旧路径和旧文件名保持不变，前缀身份只是控制面的别名。
5. 不自动搬动、重命名、删除任何旧目录或大产物。
6. 迁移期间允许总账比旧历史更保守；不得为了“补齐 v1-v23”制造未经证实的叙事。
